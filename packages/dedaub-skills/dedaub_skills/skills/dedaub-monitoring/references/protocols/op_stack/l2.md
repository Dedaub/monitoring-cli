# OP Stack native bridges, L2 side — Topics, Selectors, Addresses (Optimism + Base predeploys; OP Stack L3 settlement contracts on Base)

**Status:** verified on 2026-09-29 against live RPC on Optimism, Base and Robinhood Chain (predeploy code, EIP-1967 slots, sample transactions) and on Ethereum (link keys), the `ethereum-optimism/optimism` contracts (`packages/contracts-bedrock/snapshots/abi` at commit `54e770f157ee975592f2857c885ec831e10a0e68`, `src/libraries/Predeploys.sol`, and the tag `op-contracts/v6.0.0` for the interop contracts that the current source dropped), the OP Stack deposit specification, the Base documentation and the L2BEAT discovery files.
**Scope:** (1) the L2 predeploys at `0x4200000000000000000000000000000000000000` to `0x42000000000000000000000000000000000007fF` as deployed on Optimism (chain ID 10) and Base (chain ID 8453): the bridge, messenger, message passer, NFT bridge, token factories, WETH, fee vaults and the interop predeploys; (2) how an Ethereum deposit appears on the L2; (3) the settlement contracts of the OP Stack L3s that settle on Base. The Ethereum side of every OP Stack chain is in [l1.md](l1.md). Topics and selectors are chain-agnostic; addresses are network-specific.

Every OP Stack L2 has the same predeploys at the same addresses. Each predeploy is a 2,055-byte proxy whose implementation sits in the EIP-1967 slot and whose admin is the L2 ProxyAdmin `0x4200000000000000000000000000000000000018`. A proxy with an empty implementation slot is inactive: a call to it reverts with `Proxy: implementation not initialized` (tested on Base at `0x4200000000000000000000000000000000000023`). On Optimism and Base, **all interop predeploys are such empty proxies**, so no interop bridge is live on either chain (§3).

A deposit from Ethereum arrives as a **deposit transaction** (type `0x7e`) that the protocol creates from a `TransactionDeposited` log. It has no signature and no gas price. Its `from` is the L1 sender, aliased when the sender is a contract; for a bridge deposit it is the aliased L1CrossDomainMessenger calling the L2CrossDomainMessenger. The ETH of a deposit is **minted** (`mint` field) with no transfer event. A withdrawal starts on the L2: the L2StandardBridge calls the L2CrossDomainMessenger, which calls the L2ToL1MessagePasser; `MessagePassed` carries the `withdrawalHash` that the portal on Ethereum proves and finalizes days later.

### 1.9 What fires together on L2 (verified on the sample transactions of §12)

| Action | Transaction | Events in order | Value movement |
|---|---|---|---|
| ETH deposit relayed | Type `0x7e`, `from` = aliased L1 messenger, `to` = `0x4200000000000000000000000000000000000007`, selector `0xd764ad0b` | L2StandardBridge `DepositFinalized` (`l1Token` = zero address, `l2Token` = `0xDeadDeAddeAddEAddeadDEaDDEAdDeaDDeAD0000`) + `ETHBridgeFinalized` → messenger `RelayedMessage` | `mint` creates the ETH; internal calls pass it to the recipient. No `Transfer` event. |
| ERC-20 deposit relayed | Same | token `Transfer` from the zero address + `Mint` → `DepositFinalized` + `ERC20BridgeFinalized` → `RelayedMessage` | L1-native token: minted on L2. L2-native token: released from the L2StandardBridge escrow. |
| Failed relay | Same | messenger `FailedRelayedMessage` only | The value stays in the messenger. |
| Direct deposit (portal `depositTransaction`) | Type `0x7e`, `from` = the L1 sender (aliased if a contract), `to` = the L2 target | Whatever the target emits | `mint` credits `from` with ETH, then `value` goes to `to`. |
| ERC-20 withdrawal (`withdraw`, `withdrawTo`, `bridgeERC20To`) | User transaction | token `Transfer` to the zero address + `Burn` → bridge `WithdrawalInitiated` + `ERC20BridgeInitiated` → passer `MessagePassed` → messenger `SentMessage` + `SentMessageExtension1` | The L2 token is burned (L1-native) or escrowed in the L2StandardBridge (L2-native). |
| ETH withdrawal (`bridgeETH`, `withdraw` with the ETH token) | User transaction | bridge `WithdrawalInitiated` + `ETHBridgeInitiated` → `MessagePassed` → `SentMessage` + `SentMessageExtension1` | ETH moves into the L2ToL1MessagePasser and stays there until `burn()`. |

## 6. How an Ethereum deposit appears on the L2 (verified)

1. **Ethereum:** the portal emits `TransactionDeposited(from, to, version, opaqueData)` at log index `i` of block `B` (block hash `h`).
2. **Source hash:** `sourceHash = keccak256(bytes32(0) ‖ keccak256(h ‖ uint256(i)))`. The 0 is the domain of user deposits.
3. **Deposit transaction:** `0x7E ‖ rlp([sourceHash, from, to, mint, value, gasLimit, isSystemTx = false, data])` with the fields of `opaqueData` ([l1.md §1.1](l1.md)); `to` is empty for a contract creation. The L2 transaction hash is the keccak-256 of these bytes.
4. **L2:** the transaction is in the first L2 blocks after the L1 block (the L2 node reads each L1 block). Its receipt has `depositReceiptVersion` 1, and the transaction object shows `sourceHash` and `mint`.

Worked example (Base): Ethereum transaction `0xded9804ef44e008357adcada67ae11154b2e4d89e327c99f066f2315d454c2dd`, block 26,072,252 (hash `0xfb68d57994b92a7b08352a1af583d8f6847739a782f25a2f85bb03fd7c54da2e`), log index 691, `from` = `0x977F82a600a1414E583f7F13623F1ac5D58B1C0b` (the Base L1CrossDomainMessenger `0x866E82a600A1414e583f7F13623F1aC5d58b0Afa` + the alias offset), `mint` = `value` = 93.411170697262018787 ETH, gas limit 515,958. Computed source hash `0x8a3ac10eba1c09e44dd0ae6b43a8e68cb4c1497648af94624cd752bc22840419` and L2 hash `0x9f3b9b451e172e0b60adee5ecdcd8a08f7b87b926399aeddbdff1d5f02df7e37`. Base block 51,882,402 holds this transaction: type `0x7e`, selector `0xd764ad0b`, with `DepositFinalized`, `ETHBridgeFinalized` and `RelayedMessage` (`msgHash` `0x5688467b073db3befc163cc6d92a5a780ae7c13820cbb6aed3088bdbc3189820`, equal to the hash of the Ethereum `SentMessage`).

The withdrawal key works the same way in the other direction: `MessagePassed.withdrawalHash` = `keccak256(abi.encode(nonce, sender, target, value, gasLimit, data))` = topic1 of `WithdrawalProven` and `WithdrawalFinalized` on Ethereum (verified on `0x039db65bf11bf903632897e39e0553ee41ea1b24abcc8878585ab5261584f8ad`, withdrawal hash `0xc1b3b8d2306d05dae47b9f631275fe9bdefcaf045900c3949064ef05077f6428`).

## 10. Detection invariants & gotchas

1. **Same topic0 on every OP Stack chain and on Base's L3 contracts.** On Base, `SentMessage`, `ETHBridgeInitiated` and `TransactionDeposited` came from Base's predeploys and from the L3 contracts of §5 in the same window (`SentMessage`: 18 from `0x4200000000000000000000000000000000000007`, 2 from Horizen's messenger). Key on the emitter.
2. **One record per transfer.** `DepositFinalized` pairs with `ETHBridgeFinalized` or `ERC20BridgeFinalized`; `WithdrawalInitiated` pairs with `ETHBridgeInitiated` or `ERC20BridgeInitiated`. In the window: Base 83 `DepositFinalized` = 47 + 36; Optimism 79 = 16 + 63.
3. **Deposits mint; there is no `Transfer`.** The ETH of a deposit is created by the `mint` field of the `0x7e` transaction. A transfer dataset shows no row for it. A direct portal deposit also credits `from` with `mint` before the call.
4. **`MessagePassed` covers every withdrawal; the bridge events do not.** A call to `initiateWithdrawal` emits only `MessagePassed`. Base: 18 `MessagePassed` against 17 bridge withdrawals in the window; Optimism: 5 against 4.
5. **The ETH of a withdrawal stays in the L2ToL1MessagePasser** until someone calls `burn()` (`WithdrawerBalanceBurnt`). Treat the passer as an escrow, not as a sink.
6. **Deposit relays match across chains in the same window.** Ethereum → Base: 150 `SentMessage` at the Base L1 messenger and 150 `RelayedMessage` on Base. Ethereum → Optimism: 115 `SentMessage` and 112 `RelayedMessage` + 3 `FailedRelayedMessage` on Optimism. A gap is a failed relay or a monitoring loss.
7. **`FailedRelayedMessage` is not a payout.** The value waits in the L2CrossDomainMessenger until a replay emits `RelayedMessage` for the same `msgHash`.
8. **Aliasing.** A contract sender on L1 appears as `address + 0x1111000000000000000000000000000000001111` on L2 (the Base L1 messenger appears as `0x977F82a600a1414E583f7F13623F1ac5D58B1C0b`, the OP L1 messenger as `0x36BDE71C97B33Cc4729cf772aE268934f7AB70B2`). The `to` of a bridge event is never aliased.
9. **Interop is off.** Every interop predeploy on Optimism and Base is an empty proxy; `SendERC20`, `SendETH` and the L2ToL2 messenger events had 0 emitters in the window. Alert on `Upgraded` at `0x4200000000000000000000000000000000000022` to `0x4200000000000000000000000000000000000028`: it means interop was switched on.
10. **Same address, other contract.** On Base, the EAS implementation sits at `0xbEb5Fc579115071764c7423A4f12eDde41f106Ed`, which is OP Mainnet's portal address on Ethereum; Base's own Ethereum portal and bridge addresses hold a `Recovery` proxy on Base.
11. **An EOA controls one L3.** The ProxyAdmin of the chain 845300012 L3 is owned by the EOA `0x7d427d0eac2Dc57f0211D5f4429ECD5550e0FC35`, which can upgrade its portal and bridge on Base at once.
12. **Ham looks inactive.** Its last batch reached its inbox on 2025-11-24 and its contracts had no event in the window; B3's last batch was on 2026-09-26.
