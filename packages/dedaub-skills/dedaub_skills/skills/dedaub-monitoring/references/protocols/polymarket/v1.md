# Polymarket V1 (CTF stack) — Topics, Selectors, Addresses (Polygon PoS)

**Status:** verified against live Polygon RPC and the canonical `Polymarket/ctf-exchange`, `Polymarket/neg-risk-ctf-adapter`, `Polymarket/uma-ctf-adapter`, `Polymarket/exchange-fee-module`, `Polymarket/uma-sports-oracle` and `Polymarket/proxy-factories` repos on 2026-10-30.
**Scope:** the original Polymarket order-book stack on Polygon PoS (137). It covers the Gnosis Conditional Tokens Framework (CTF), CTF Exchange, NegRisk CTF Exchange, NegRiskAdapter, NegRiskOperator, fee modules, UMA CTF adapters, UMA Sports Oracle, proxy-wallet and Safe factories, USDC.e collateral, and the legacy FPMM AMM. Topics and selectors are chain-agnostic. Addresses are network-specific. The trading stack is **Polygon-only**. §5 records the result on the other eight chains.

Polymarket is a central-limit-order-book (CLOB) prediction market. Orders are matched off-chain by an operator. Settlement is on-chain: the operator calls `matchOrders` / `fillOrders` on the exchange. Every outcome share is an ERC-1155 position token of the Gnosis CTF (`0x4d97…6045`). Collateral in this stack is **USDC.e** (bridged USDC, `0x2791…4174`).

Trading moved to CTF Exchange V2 (`exchange_v2.md`) in late April to May 2026. The V1 exchanges emitted about 16,000 logs per 60 blocks at block 86.0M, a few dozen at 88.0M–88.7M, and none in samples after 88.9M. The CTF, NegRiskAdapter, WCOL and the UMA adapters stay in use, because the V2 exchanges settle through them.

All V1 contracts are **immutable** (no EIP-1967 slots). Polymarket rotated components by redeploying them, so each component has several generations (UMA adapter V1 → V2 → V3.1 → V4; NegRisk fee module old → new; NegRiskOperator first → second). Old generations stay deployed and some still emit events. Index all of them.

Negative-risk ("neg-risk") markets use a separate path. The NegRiskAdapter wraps USDC.e into `WrappedCollateral` (WCOL) and calls the CTF with WCOL as collateral. The NegRisk CTF Exchange treats the **NegRiskAdapter** as its "CTF". So neg-risk positions are CTF tokens on `0x4d97…6045` whose collateral is WCOL, not USDC.e.

## 7. Detection invariants & gotchas

1. **One trade, several `OrderFilled`.** `matchOrders` emits one `OrderFilled` per maker order plus one for the taker order, then one `OrdersMatched`. Sum maker fills or use `OrdersMatched`. Do not add both.
2. **`OrderFilled` asset ids.** V1 has `makerAssetId` and `takerAssetId`. The id `0` means collateral (USDC.e). The non-zero id is the CTF position id. Side = BUY when `makerAssetId == 0`.
3. **Amounts are 6-decimal.** USDC.e and outcome tokens both use 6 decimals. Price = collateral amount / share amount.
4. **The real user is the `maker`, which is usually a proxy wallet or Safe**, not an EOA. Map with `getPolyProxyWalletAddress` / `getSafeAddress`, the Safe `ProxyCreation` event, or traces into ProxyWalletFactory. `taker` is often the exchange itself in `matchOrders`.
5. **Operator-only settlement.** `msg.sender` of trade transactions is a Polymarket operator EOA (or a fee module). Alert on `NewOperator` / `RemovedOperator` / `NewAdmin` on the exchanges.
6. **Neg-risk collateral is WCOL.** CTF `PositionSplit` from neg-risk flows has `collateralToken` = WCOL `0x3a3b…02e2`. The NegRisk exchange `getCtf()` is the adapter, not the CTF.
7. **Resolution paths.** Binary: UMA adapter → `CTF.reportPayouts` → `ConditionResolution` (oracle = adapter). Neg-risk: NegRisk UMA adapter → NegRiskOperator `QuestionReported` → `resolveQuestion` → NegRiskAdapter `OutcomeReported` → CTF `ConditionResolution` (oracle = adapter `0xd91e…5296`).
8. **Emergency resolution is an admin action.** Watch `QuestionEmergencyResolved` (V2/V3.1: `bytes32,uint256[]`; operator: `bytes32,bool`), `QuestionManuallyResolved` (V4), `GameEmergencySettled` and `MarketEmergencyResolved` (sports). Also watch `QuestionFlagged`, `QuestionReset`, `QuestionPaused`.
9. **Two NegRiskOperators are live.** The second (`0x6619…2e93`) pairs with NegRiskUmaCtfAdapter V4. It is not in `neg-risk-ctf-adapter/addresses.json`.
10. **`ConditionResolution.oracle`** tells which adapter resolved a market. Use it to attribute resolutions to adapter generations.
11. **Fee modules wrap the exchange.** When a fee module is the operator, the exchange `FeeCharged` shows the gross fee. The module then emits `FeeRefunded` for the refund to the maker.
12. **Legacy FPMM markets** still hold CTF positions. Their trades emit `FPMMBuy` / `FPMMSell` from per-market FPMM clones, not from the factory.

## 9. Verification & sources

How constants in this doc were verified (2026-10-30):
- **Topic0 / selectors:** recomputed locally as `keccak256(signature)` from the Solidity sources. Each topic0 was then found as a `PUSH32` operand, and each selector as a `PUSH4` dispatcher operand, in the live Polygon bytecode of the emitting contract. The V1 UMA adapter and FPMM topics come from the ABIs in the `Polymarket/resolution-subgraph` and `Polymarket/polymarket-subgraph` repos.
- **Live events:** V1 `OrderFilled` (`0xd0a0…`) and `OrdersMatched` (`0x63bf…`) seen on CTFExchange at block 75,000,000. A 40-block sample at the chain head (96,445,769–96,445,809) showed all eight CTF topics in §1.1, six NegRiskAdapter topics, WCOL `Transfer`, UmaCtfAdapter V4 `QuestionResolved` and NegRiskUmaCtfAdapter V4 `QuestionInitialized`.
- **Addresses:** taken from `neg-risk-ctf-adapter/addresses.json`, `ctf-exchange/README.md`, `proxy-factories/README.md`, `uma-sports-oracle/README.md`, `polymarket-subgraph/networks.yaml`, `resolution-subgraph/networks.json` and the `clob-client-v2` contract config. Each address was existence-checked with `eth_getCode`. Wiring (`getCollateral`, `getCtf`, `col`, `wcol`, `vault`, `oracle`, `ctf`, `optimisticOracle`, `exchange`) was read live. The second NegRiskOperator was found through `NegRiskUmaCtfAdapterV4.ctf()`.
- **Proxies:** EIP-1967 implementation, admin and beacon slots read for every address. All V1 contracts returned zero.
- **Chain coverage:** every address was checked on all nine chains. Non-empty code on a non-Polygon chain was compared by size and code hash with Polygon. The factory replicas have identical hashes. The `0x2791…`/`0xee3a…` Ethereum hits have different code.
